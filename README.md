## 自己PR・志向性

Webフロントエンドを中心に15年の開発経験があります。仕様・UXの検討からUIの設計・実装まで、一貫して取り組むことが強みです。ユーザーが「説明なしで使える」ことを一つの基準に、プロダクトの使いやすさを追求してきました。

動画プレイヤーのライブラリ選定やジョイスティックUIのスクラッチ開発など、ユーザー体験と技術的な実現性の両面から技術を選び、プロダクトとして形にしてきました。

現在はAI英語学習サービス「abceed」のWebチームリーダーとして、自ら開発を行いながら、採用・技術選定・仕様調整・プロジェクト推進まで幅広く担っています。

## 開発で大切にしていること

### 「説明なしで使えるUI」を追求し続ける

Flash時代から、ユーザーが操作そのものを意識せずに使えるUIづくりにこだわってきました。ボタン一つでも、派手なアニメーションで目を引いて押してもらうのではなく、自然と触りたくなるような、心地よいものを生み出したい。そうした小さな心地よさの積み重ねが、「説明なしで使えるUI」につながると考えています。

目の前の仕様やデザインをそのまま実装するのではなく、「ユーザーが迷わないか」「使いづらいところはないか」を常に考えています。気づいた課題には改善案を添え、PdMやデザイナーと相談しながら、「説明なしで使えるUI」を追求し続けています。

### まずはやってみる。失敗したら別の方法を試せばいい

新しい技術を採用するときや、実現性の判断に迷うときは、「まずやってみる」精神でプロトタイプを作って検証しています。たとえ失敗しても、その方法ではうまくいかないとわかることに価値があります。次は別の方法を試せばいい。そうした姿勢で、技術選定や実現性の判断を行ってきました。

得られた知見や判断の過程は、チーム内で共有したり、技術記事として外部に発信したりしています。同じ迷いに直面した人の助けになればと考えています。

### チームが開発しやすい環境を整える

要件整理からタスクの作成、担当の割り振り、レビュー、QA前の検証まで、開発全体に関わってきました。AIの活用によって開発量が増える中、メンバーへ役割を引き継ぎ、仕様の相談に乗ったり、進行上の課題の解決を支援したりしています。自分で開発するだけでなく、メンバーが自分で判断し、開発を進められるようにすることを大切にしています。

#### AI英語学習サービス「abceed」のWebフロントエンド開発

**期間：** 2021年3月 〜 現在
**役割：** フロントエンドリード

**概要：**
AI英語学習サービス「abceed」のWebフロントエンド開発をリード。ユーザー向け機能・管理画面の設計・実装に加え、PdM・デザイナーと連携した仕様整理やUI/UX改善、技術選定まで担当。

担当するWeb版は個人の英語学習に加え、企業研修や学校でのTOEIC・英検対策にも利用されている。学校でのChromebook利用やPCの大画面での学習に対応。SNS・他サービスからの利用者の受け入れや、Web限定機能の提供も担っている。

**課題と取り組み：**

##### Webに最適化した仕様・UI設計

共通機能の多くは、利用者の多いiOS / Androidアプリの仕様・デザインを先に検討し、その後Web版を設計していた。Web限定機能は初めからWeb向けに検討。Webチームは各アプリチームと同じ人数で管理画面も開発しており、対応範囲に対して人員が限られていた。

- 実装後の手戻りを防ぐため、実装前にデザインをレビュー。リロード時の状態管理、ナビゲーションガード、ブラウザからフォーカスが外れた際の処理など、Web固有のユースケースを洗い出し、PdM・デザイナーと仕様やUIを具体化
- 自身の担当以外のプロジェクトでもデザインや実装後の挙動を積極的に確認し、レスポンシブ表示、例外時のレイアウト、仕様で明示されていないユースケースなどをフィードバック

##### AI英会話のフリートーク機能におけるUI改善（2026年夏リリース）

- シチュエーションの詳細を別画面で表示する設計では、選び直すたびに一覧へ戻る必要があった。この手間を減らすため、一覧画面上のモーダルで詳細を表示する方式を提案
- PCの画面幅ならモーダル内に詳細を表示できる。一方、別画面ではリロード時の表示やデータ取得を考慮する必要がある。これらをデザイナーと共有し、提案が採用された
- 一覧を離れずに詳細の確認と選び直しができるようになり、画面遷移を削減。一覧で取得済みのデータを再利用することで、予定していた追加のAPI呼び出しも不要にした

##### 映画・ドラマを使った英語学習機能の動画プレイヤー開発（2023年春リリース）

- 映画会社のライセンス条件であるDRMによる著作権保護と、学習者が気になった台詞へ移動してスムーズに聞き直せる操作を両立する必要があった
- 既存のHLS資産を活用できるhls.jsでプロトタイプを構築し、早期に学習に適したUI/UXを検証。映画会社の担当者に実際の学習体験を説明するためにも活用
- 本実装ではDRM対応のためVideo.jsを採用。しかし、動画の途中から再生を始め、フレーズを素早く戻す操作を繰り返して再生開始位置より前に移動すると、動画が停止した。調査しても解決に至らず、台詞をスムーズに聞き直せる学習体験を優先してライブラリを再選定
- DRM対応のOSS・有料ライブラリを調査し、DRMのサンプルが豊富なShaka Playerで検証。Video.jsで問題が起きた操作でも、速やかに再生が再開することを確認して採用した。再生停止を解消し、著作権保護とスムーズなフレーズ再生を両立
- 詳しくは[abceed webの映画・ドラマ機能開発で使用した動画ライブラリの変遷](https://qiita.com/umi_kappa/items/f91eb2ed1ea3e0594992)をご覧ください

##### SNSシェア機能の改善

- 学習状況をSNSに共有する機能では、ブラウザで生成した画像を利用者が手動でSNSに添付する必要があり、実装時から操作の手間を課題と捉えていた
- 機能の再検討時に、共有ページのURLをSNSへ渡す方式をPdM兼CTOに提案。学習結果に応じたOGPを設定した共有ページを生成する構成とした。投稿を見た人がabceedへ移動できるよう、共有ページ内へのリンク設置も提案
- OGPの動作を事前に調査し、共有ページのHTMLテンプレートとクライアント側のシェア操作を実装。サーバー側の実装はサーバーチームが検討した。テンプレートに渡すデータ形式などは同チームと相談しながら、開発を進めた
- 本番リリース後は、abceed内のシェアボタンを押すと、共有URLが入力されたSNSの投稿画面が開くようになった。画像を手動で添付する操作を不要にし、学習結果を共有する手間を削減

**技術スタック：** TypeScript, Vue.js, Vuex, Pinia, Vite, webpack, Vitest, Storybook, Chromatic, GitHub Actions, Shaka Player

#### Webフロントエンドチームのリード・開発プロセス改善

**期間：** 2021年3月 〜 現在
**役割：** チームリーダー

**概要：**
Webフロントエンドチームの立ち上げ期から、プロジェクト推進、採用、開発・レビュー環境の整備などを担当。自ら開発にも携わりながら、チーム全体の開発をリード。

Webチームは入社時に自身を含め2名。その後、最大4名まで拡大し、現在は3名体制。2名体制の時期には、別途業務委託1名が参画した。プロジェクトでは、iOS・Android・サーバーの各エンジニア、デザイナー、PdM、QAなど、各職種のメンバーと連携して開発を推進。

**課題と取り組み：**

##### プロジェクト推進・役割分担

- チーム立ち上げ期は、要件・仕様整理、技術調査、UI/UX検討、URL設計、Issue作成、アサイン、PRレビュー、QA前検証までプロジェクト推進を幅広く担当
- AI活用に伴い、会社として進めたいプロジェクトの数とレビュー量が増加。自身も開発を担当していたが、仕様調整やレビューに時間を取られ、担当プロジェクトの進行が遅れることが増えていた
- 2026年から、仕様策定・デザイン調整やレビューを含むプロジェクト推進をメンバーへ段階的に移譲
- 現在は各プロジェクトの進行状況や課題を把握し、既存仕様に関する質問や設計の相談に対応。必要に応じてメンバーに代わり、関係者との調整も担当。こうした支援を続けながら、自身が開発に充てられる時間を再び確保できるようになってきた

##### Webの仕様・デザインの検討漏れを防ぐチェックリストの導入

- iOSエンジニア・デザイナー・PdMが先行して仕様やデザインを検討し、Webメンバーが後から参加するプロジェクトが多かった。Webメンバーの参加時点では、Web向けに必要な仕様やデザインが固まっておらず、すぐに実装へ着手できないことが課題だった
- 開発の進めづらさをCTOに相談し、Webメンバーが初期から参加しない場合でも必要な観点を事前に確認できるよう、チェックリストの導入を提案
- リロードやURLへの直接アクセス時の挙動、ホバー時のデザイン、画面幅の変更への対応などをNotionに整理。仕様・デザインの検討段階で、AIにこの資料を参照させて検討漏れを確認する運用を提案し、CTOの合意を得た
- PdMや先行して参加するエンジニアが、チェックリストを使ってAIで確認するようになった。リロード時の挙動が事前に議論され、ホバー時のデザインもWebメンバーの参加前に用意されるケースが増えた

##### AIを活用した開発プロセス改善

- 2026年からClaude Codeを日常的な開発に導入し、要件をもとにした設計・実装プランの策定から、実装・テスト・コードレビューまで開発プロセス全体で活用
- API関連ファイルの一括生成やPRレビューなど、繰り返し発生する開発業務の手順をClaude CodeのSkillにまとめ、再利用・自動化できるように整備
- 2026年からSkillをリポジトリで共有し、チームメンバーとアイデアを持ち寄って議論・改善しながら、チーム共通の開発プロセスとして継続的に整備

##### フロントエンドエンジニア採用

- シニアクラスのフロントエンドエンジニア採用で、コーディング試験の改善・運用と技術面談を担当
- 2026年から、AIによる実装支援の普及を踏まえ、実装力だけでなく曖昧な要件を整理して仕様に落とし込む力も評価できるよう試験内容を改善

##### コンポーネント開発・レビュープロセス改善

- 目的のコンポーネントをアプリケーション上で確認するには、画面を移動し、必要な状態を再現する手間がかかっていた
- 2021年3月の入社時にStorybookの導入を提案・実施し、アプリケーション全体を操作せずコンポーネント単位でUI・挙動を確認できる開発環境を整備
- 2025年にメンバーの提案をもとにChromaticを導入し、チームで運用を整備。Visual Regression Testingによる意図しないUI差分の検出や、オンラインのStorybookを利用したPRレビューを実現

### 個人開発（2026年4月 〜 現在）

**ポジション：** フロントエンドエンジニア

#### [PeakRM](https://github.com/umi-kappa/peak-rm)（トレーニング記録・1RM可視化Webアプリ）

**期間：** 2026年4月 〜 現在
**役割：** 企画・設計・実装

**概要：**
トレーニング記録、推定1RMによる成長の可視化、インターバル管理を一つにまとめたWebアプリを個人開発。自身のトレーニングでは、記録を紙で管理し、インターバルを別のタイマーアプリで計測していた。この不便を解消するために開発を始めた。企画、仕様整理、UX設計、UIデザイン、アーキテクチャ設計、実装まで一貫して担当。現在リリースに向けて開発中。

**課題と取り組み：**

- **AIを活用した開発における設計・UIの一貫性**
  - [仕様書](https://github.com/umi-kappa/peak-rm/blob/main/docs/spec.md)・[コーディング規約](https://github.com/umi-kappa/peak-rm/blob/main/docs/conventions.md)・[デザインドキュメント](https://github.com/umi-kappa/peak-rm/tree/main/docs/design)を整備。AIを活用した開発でも、設計判断・実装方針・UIの一貫性を維持できる開発環境を構築
  - Figmaなどのデザインツールを使用しない代わりに、UIの方針や判断基準をデザインドキュメントとして管理

- **トレーニング中の利用を想定したUI/UX設計**
  - 自身がジムで記録やインターバル管理を行う場面をもとに、必要な機能と操作フローを設計
  - セット間の短い時間でも迷わず操作できるよう、記録入力・成長の確認・インターバル計測を一つのアプリ内で完結できるUIを設計

- **ローカルファースト・オフライン対応**
  - リリースまでの開発コストを抑えつつ、通信環境が安定しないジムでも利用できるよう、バックエンドへの常時接続を前提としない構成を採用
  - IndexedDB（Dexie）によるローカルファースト設計とPWA化により、ログイン不要で、オフラインでも利用できるアプリケーションを実装

**技術スタック：** TypeScript, Vue.js, Vite, IndexedDB（Dexie）, PWA, Chart.js, Vitest, Storybook, Chromatic, GitHub Actions
